## 1. НАЗНАЧЕНИЕ ФАЙЛА

AEDIS — шаблон Baseline 0: корпус документов, описывающий сам себя и опирающийся только на собственные правила. Оператор — единственная решающая власть. Контуры LLM: Gemini — исполнитель в Google AI Studio; Kimi — аудитор GitHub в режиме read-only.

Дефект процесса: поток решений Оператора опережал фиксацию в корпусе. Решения оставались в диалоге, корпус не обновлялся, проект фактически существовал вне корпуса — накапливался дрейф: решения принимались без фиксации, трассировки и проверки.

Решение Оператора (2026-10-12): существует ровно одна точка накопления идей — этот файл, на языке Оператора (русский). Идея существует для проекта тогда и только тогда, когда зафиксирована здесь. Запись удаляется из файла только по правилам R3.

Русский язык — ратифицированное Оператором отклонение от ADR-L0-000003/R5: файл — ненормативная поверхность, не корпус. Регистр — технический: термины только из глоссария (./aedis/governance/specs/glossary.md), без метафор, без новых сущностей. Отсутствующий термин регистрируется как задача на проработку (TASK-004).

Диалог не является носителем решений. Данный файл является единственной точкой фиксации решений Оператора и одновременно картой открытых долгов: первая запись очереди — точка, с которой положено начинать. Всё содержательное из диалога обязано быть перенесено в этот файл.

## 2. ПРАВИЛА

ДЕФИНИЦИИ:
- МЕЛКАЯ ПРАВКА (CLASS_MINOR_EDIT) = скоуп из ровно одного фрагмента в ровно одном документе корпуса.
- КРУПНАЯ ДОРАБОТКА (CLASS_MAJOR_REWORK) = скоуп из двух и более фрагментов или из двух и более документов корпуса.
- СКОУП = полный, исчерпывающий перечень документов, разделов и фрагментов корпуса, которые изменяет внедрение идеи. Скоуп определяется на этапе регистрации — до анализа решения и до внедрения. Скоуп — проверяемый список изменений, а не описание намерения.
- ФРАГМЕНТ = один смежный блок верхнего уровня структуры документа (абзац, элемент списка, заголовок, таблица, текстовый блок). Создание и удаление документа корпуса относятся к классу КРУПНАЯ ДОРАБОТКА.
- ИСПОЛНЕНИЕ = один запуск исполнителя по одной задаче T1; результат — ровно один коммит со всеми изменениями скоупа; в поле (4) вносится SHA этого коммита.
- АКТИВНАЯ ЗАПИСЬ = единственная запись с установленным Ф2, без Ф3, с ОЖИДАЕТ: нет.
- ЗАПИСЬ В ИСПОЛНЕНИИ = запись с Ф3 = ОДОБРЕНО ВНЕДРЕНИЕ без Ф4. Блокировка записи допускается до установки Ф4.
- ОЖИДАНИЕ = состояние записи с непустым полем ОЖИДАЕТ. Запись выходит из ожидания после закрытия всех записей, перечисленных в её списке ОЖИДАЕТ.
- ГЛУБИНА ЦЕПОЧКИ БЛОКИРОВОК = число рёбер ОЖИДАЕТ в самом длинном пути графа.
- РАЗДЕЛЕНИЕ = диспозиция по R8: исходная запись заменяется двумя и более записями с меньшим скоупом; поле (1) каждой новой записи дословно ссылается на исходный текст Ф1; флаги Ф2–Ф4 не наследуются.
- СОСТОЯНИЕ РАСХОЖДЕНИЕ = состояние корпуса, при котором последний коммит исполнения не прошёл верификацию по R12 или против T1. В состоянии РАСХОЖДЕНИЕ активация других записей запрещена.
- РЕШЕНИЕ ОПЕРАТОРА = во всех правилах формулировка «совместное решение Оператор+LLM» означает: решение принимает Оператор после изложения позиции LLM; возражение LLM не блокирует решение.
- ИДЕНТИФИКАТОР ПРАВИЛА (R[NN]) = документно-локальный машиночитаемый токен. Голый идентификатор R[NN] допустим только внутри данного файла. Внешние ссылки на правило оформляются в квалифицированной форме: [DOC-ID]:R[NN]. Универсальных для шаблона идентификаторов R не существует.

Класс записи определяется формальным критерием — количеством фрагментов и документов в скоупе, а не по оценке.

- R0 САМОПРИМЕНЕНИЕ: ни один документ не коммитится при противоречии корпусу. Каждое положение проверяется на конфликт с ADR-L0-000001…ADR-L0-000013; конфликт устраняется правкой либо регистрируется в разделе «Сознательные отклонения» по чартеру §7. Решение об устранении правкой либо о регистрации отклонения принимает Оператор. Метафоры заменяются терминами глоссария до коммита.
- R1 ЕДИНСТВЕННАЯ ТОЧКА: все идеи и решения Оператора фиксируются только здесь. Других мест накопления нет.
- R2 ЯЗЫК И РЕГИСТР: русский; технический регистр; термины только из глоссария; метафоры запрещены.
- R3 ОСНОВАНИЯ УДАЛЕНИЯ ЗАПИСЕЙ (исчерпывающий перечень): записи дополняются. Удаление записи выполняется в трёх случаях: (а) при наличии четырёх флагов и совместном решении Оператор+LLM; (б) при диспозиции СИНТЕЗ или ЗАМЕЩЕНИЕ на этапе регистрации либо диспозиции РАЗДЕЛЕНИЕ по R8 — по совместному решению Оператор+LLM; (в) при резолюции ОТКЛОНЕНО или ДУБЛЬ, вынесенной на любой стадии после регистрации, — по решению Оператора; причина фиксируется в поле (3). Других оснований для удаления записи нет.
- R4 СЕРИЙНОСТЬ: в работе находится строго одна идея. Активная запись (дефиниция в разделе 2) — единственная. Фиксация (Ф1) выполняется параллельно и не ограничена: наличие Ф1 не блокирует другие записи. Работа над записью начинается с активации — установки Ф2. Активация без утверждённого скоупа и выполненной проверки R10 запрещена.
- R5 ВНЕДРЕНИЕ НА ВЕСЬ КОРПУС: одобренная идея изменяет все документы корпуса, которые затрагивает, в одном исполнении. Частичное внедрение запрещено. Операциональное определение: «весь корпус, который затрагивает идея» = скоуп записи.
- R6 ДИНАМИЧЕСКАЯ ОЧЕРЕДЬ: записи класса МЕЛКАЯ ПРАВКА размещаются в начале очереди; записи класса КРУПНАЯ ДОРАБОТКА — в конец. Мелкие правки закрываются первыми. Ожидаемый эффект (не правило): объём крупных доработок уменьшается по мере закрытия мелких правок. Порядок очереди вычисляется по настоящему правилу и не хранится в файле. Хранение порядка запрещено.
- R7 ZERO-ШАБЛОН: корпус — нулевой шаблон. Эратумы, новые ADR и чейнджлоги не создаются. Все версии документов — 1.0.0. Внедрение идеи = прямая правка текста корпуса.
- R8 ПЕРЕГРУЗ СЕССИИ: если внедрение не укладывается в одну сессию или один scope-lock T1 — работа останавливается. Порог «одна сессия» определяется Оператором. Запись выходит из работы с пометкой ПРЕВЫШЕНИЕ ЛИМИТА. Оператор выбирает диспозицию РАЗДЕЛЕНИЕ либо изменение лимита с повторным Ф3. Параллельно идея фиксируется в файле DEBT (./aedis/governance/specs/debt/) с последовательностью документов (зависимости первыми); обработка записей DEBT отложена до релиза (DEV-002), поэтапное исполнение по записям DEBT до закрытия DEV-002 запрещено. Молчаливое дробление запрещено (чартер §6).
- R9 ПАМЯТЬ КОНТУРА: промежуточное состояние и полное описание текущей задачи фиксируются в памяти контура (state-файл) для продолжения в чистой сессии.
- R10 АНТИДУБЛЬ: при регистрации новой идеи контур LLM выполняет поиск похожей невнедрённой записи. Критерий похожести до появления линтера определяется полным обсуждением Оператор+LLM: контур LLM выполняет поиск, Оператор направляет поиск. При совпадении диспозиция определяется до регистрации: СИНТЕЗ (обе идеи объединяются в одну запись, прежние записи удаляются) или ЗАМЕЩЕНИЕ (старая запись удаляется с фиксацией причины, регистрируется новая). СИНТЕЗ и ЗАМЕЩЕНИЕ допускаются только для записей без установленного Ф2. Идея без определённой диспозиции не регистрируется. Параллельное существование двух близких идей запрещено.
- R11 ПОЛНАЯ СВЕРКА ПРИ АВТОРИНГЕ: перед ратификацией текста контур LLM выполняет сверку по полному списку запрещённых конструкций Strict AEDIS CommonMark Profile (раздел Forbidden AST профиля 1.5), а не по выборочным пунктам. Самопроверка исполнителя не является достаточной верификацией; финальная сверка выполняется по чек-листу Forbidden AST целиком, включая текстовые блоки, плейсхолдеры шаблонов и обозначения параметров идентификаторов. Угловые скобки в потоковом тексте запрещены во всех контекстах; плейсхолдеры и параметры идентификаторов оформляются квадратными скобками.
- R12 СКОУП ОБЯЗАТЕЛЕН: скоуп каждой идеи определяется при регистрации — до анализа решения и до внедрения. Флаг 3 не выдаётся без зафиксированного скоупа. Флаг 4 сверяет фактический diff по commit SHA исключительно со скоупом: любое расхождение diff со скоупом = провал верификации, эскалация Оператору по §P6. Сверка выполняется на равенство: изменение вне скоупа и неизменённый элемент скоупа — оба провал. Изменения самого файла интейка в сверку не входят. Скоуп полный независимо от класса записи: перечисляются все затрагиваемые документы и фрагменты. До Ф3 скоуп уточняется Оператором (по результатам Ф2, R10, проверки вхождений раздела 5); класс записи пересчитывается при каждом изменении скоупа. После Ф3 скоуп неизменен; его изменение аннулирует Ф3 и требует повторного Ф3.
- R13 БЛОКИРОВКА: если закрытие записи на любой стадии до Ф4 невозможно без выполнения других записей, работа над ней останавливается. В запись вносится поле ОЖИДАЕТ: [список IDEA-YYYY-NNN | нет] — ссылки на блокирующие записи. Блокирующие записи регистрируются (Ф1); каждая проходит цикл до закрытия. Запись выходит из ожидания после закрытия всех записей её списка; активация — по разделу 6. При закрытии блокирующей записи без Ф4 (ОТКЛОНЕНО, ДУБЛЬ, СИНТЕЗ, ЗАМЕЩЕНИЕ) диспозиция ссылок ОЖИДАЕТ определяется Оператором: перенаправление ссылки на запись-замену, изменение скоупа ожидающей записи (аннулирует Ф3), либо ОТКЛОНЕНО. Глубина цепочки более 3 — эскалация Оператору: расширение скоупа (аннулирует Ф3) или остановка (связка с R8). Граф ОЖИДАЕТ-ссылок обязан быть ацикличным; циклическая ссылка запрещена.

## 3. ЖИЗНЕННЫЙ ЦИКЛ: ЧЕТЫРЕ ФЛАГА

Идея считается выполненной только при наличии всех четырёх флагов рядом с записью.

- Ф1 ВЫСКАЗАНО ОПЕРАТОРОМ: verbatim-текст. Ставится немедленно при высказывании идеи (операционализация чартера §5: немедленная регистрация, а не немедленная ратификация). Фиксация параллельна и не ограничена. Запись допускает СКОУП: НЕ ОПРЕДЕЛЁН; утверждение скоупа и проверка R10 выполняются до активации записи (R4).
- Ф2 ПОНЯТО LLM: контур LLM формулирует переформулировку на техническом языке. Ф2 устанавливается при активации записи; активная запись единственна (R4). Если однозначная переформулировка невозможна — флаг не ставится; Оператор дописывает уточнение к полю (1) с датой (исходный текст сохраняется) либо выносит резолюцию ОТКЛОНЕНО (R3(в)).
- Ф1+Ф2 ОДОБРЕНЫ СОВМЕСТНО: ЖЕЛАТЕЛЬНО совместное обсуждение Оператор+LLM с ожиданием позиции LLM. Данный шаг не является блокирующим условием перехода.
- Ф3 РЕЗОЛЮЦИЯ: ОДОБРЕНО ВНЕДРЕНИЕ. Вердикт Оператора в интерактивной сессии (Verification Seal, §P6). Вердикт не выдаётся без зафиксированного скоупа. Исходы: ОДОБРЕНО, ОТКЛОНЕНО (с причиной), ДУБЛЬ (со ссылкой). Резолюции ОТКЛОНЕНО и ДУБЛЬ допускаются на любой стадии после регистрации; запись с такой резолюцией выводится из работы и ожидания и удаляется по R3(в). Диспозиция отклонённых и дублирующих записей определяется при внесении (R10); нерешённая запись не вносится.
- Ф4 ВНЕДРЕНО: Gemini исполнил задачу T1 (дефиниция ИСПОЛНЕНИЕ); Kimi верифицировала diff по commit SHA со скоупом записи; Оператор и LLM совместно принимают решение «в архив» — и только после этого запись удаляется.

Обработка записей DEBT на стадии разработки не выполняется: все записи DEBT будут удалены к релизу шаблона, формальная обработка по DEBT-FSM (ADR-L0-000001/R2.3) отложена. См. раздел «Сознательные отклонения».

## 5. ПОРЯДОК РАБОТЫ

1. РЕГИСТРАЦИЯ: идея озвучена → запись с флагом 1 немедленно (Ф1 допускает СКОУП: НЕ ОПРЕДЕЛЁН) → контур LLM выполняет проверку R10, Оператор направляет поиск → при совпадении: диспозиция СИНТЕЗ или ЗАМЕЩЕНИЕ → скоуп формулирует контур LLM под направлением Оператора, утверждает Оператор (R12). Активация записи без утверждённого скоупа и выполненной проверки R10 запрещена (R4).
2. ПОНИМАНИЕ: переформулировка контуром LLM (флаг 2) при активации записи → ЖЕЛАТЕЛЬНО совместная сверка с Оператором. Ф2 устанавливается только на активную запись. При невозможности переформулирования — возврат Оператору по Ф2 (раздел 3).
3. БЛОКИРОВКА (условный шаг): при невозможности закрыть запись до Ф4 без других записей — R13: поле ОЖИДАЕТ со списком блокирующих записей, каждая блокирующая запись регистрируется и проходит цикл.
4. РЕЗОЛЮЦИЯ: вердикт Оператора (флаг 3) при зафиксированном скоупе.
5. ИСПОЛНЕНИЕ: Kimi авторит задачу T1 (scope-lock на все затрагиваемые документы; scope-lock T1 идентичен скоупу записи) → Gemini исполняет без интерпретации → синхронизация с GitHub.
6. ВЕРИФИКАЦИЯ: Kimi проверяет diff по commit SHA против T1 и сверяет diff со скоупом записи на равенство (R12). Расхождение diff со скоупом или провал против T1 — стоп по §P6, эскалация Оператору; корпус переходит в состояние РАСХОЖДЕНИЕ. Дополнительно контур-аудитор выполняет поиск по корпусу каждого изменённого или удалённого идентификатора и термина; вхождения вне скоупа перечисляются Оператору. Любое вхождение вне скоупа — эскалация по §P6; решение об изменении скоупа или отклонении принимает Оператор. Проверка выявляет ссылочные расхождения; смысловые расхождения остаются предметом Ф2. Оператор выбирает: (а) revert коммита исполнения и повторное исполнение той же задачи T1; (б) изменение скоупа с аннулированием Ф3 и повторным Ф3; (в) резолюция ОТКЛОНЕНО с revert коммита исполнения. До решения Оператора состояние РАСХОЖДЕНИЕ сохраняется.
7. АРХИВАЦИЯ: совместное решение Оператор+LLM (флаг 4) → запись удаляется из файла → записи, ссывавшиеся на неё полем ОЖИДАЕТ, выходят из ожидания; активация — по разделу 6.

## 6. ОЧЕРЕДЬ

Очередь динамическая. Порядок очереди вычисляется по правилам R6 и R13 и не хранится в файле. Приоритет: (1) блокирующие записи — цели поля ОЖИДАЕТ записей в ожидании; (2) записи класса МЕЛКАЯ ПРАВКА по дате регистрации; (3) записи класса КРУПНАЯ ДОРАБОТКА.
