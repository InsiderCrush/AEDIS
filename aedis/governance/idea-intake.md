## 1. НАЗНАЧЕНИЕ ФАЙЛА

AEDIS — шаблон Baseline 0: корпус документов, описывающий сам себя и опирающийся только на собственные правила. Оператор — единственная решающая власть. Контуры LLM: Gemini — исполнитель в Google AI Studio; Kimi — аудитор GitHub в режиме read-only.

Дефект процесса: поток решений Оператора опережал фиксацию в корпусе. Решения оставались в диалоге, корпус не обновлялся, проект фактически существовал вне корпуса — накапливался дрейф: решения принимались без фиксации, трассировки и проверки.

Решение Оператора (2026-10-12): существует ровно одна точка накопления идей — этот файл, на языке Оператора (русский). Идея существует для проекта тогда и только тогда, когда зафиксирована здесь. Запись удаляется из файла только по правилам R3.

Русский язык — ратифицированное Оператором отклонение от ADR-L0-000003/R5: файл — ненормативная поверхность, не корпус. Регистр — технический: термины только из глоссария (./aedis/governance/specs/glossary.md), без метафор, без новых сущностей. Отсутствующий термин регистрируется как задача на проработку (TASK-004).

Диалог не является носителем решений. Данный файл является единственной точкой фиксации решений Оператора и одновременно картой открытых долгов: первая запись очереди — точка, с которой положено начинать. Всё содержательное из диалога обязано быть перенесено в этот файл.

## 2. ПРАВИЛА

ДЕФИНИЦИИ:
- МЕЛКАЯ ПРАВКА (CLASS_MINOR_EDIT) = скоуп из ровно одного фрагмента в ровно одном документе корпуса.
- КРУПНАЯ ДОРАБОТКА (CLASS_MAJOR_REWORK) = скоуп из двух и более фрагментов или из двух и более документов корпуса.
- СКОУП = полный, исчерпывающий перечень документов, разделов и фрагментов корпуса, которые изменяет внедрение идеи. Скоуп определяется на этапе регистрации — до анализа решения и до внедрения. Скоуп — проверяемый список изменений, а не описание намерения.
- АКТИВНАЯ ЗАПИСЬ = запись с Ф2 без Ф3. Активная запись единственна.
- ОЖИДАНИЕ = состояние записи с полем ОЖИДАЕТ, ссылающимся на блокирующую запись. Ожидающая запись не является активной; после закрытия блокирующей записи ожидающая активируется.
- ИДЕНТИФИКАТОР ПРАВИЛА (R&lt;NN&gt;) = документно-локальный машиночитаемый токен. Голый идентификатор R&lt;NN&gt; допустим только внутри данного файла. Внешние ссылки на правило оформляются в квалифицированной форме: [DOC-ID]:R&lt;NN&gt;. Универсальных для шаблона идентификаторов R не существует.

Класс записи определяется формальным критерием — количеством фрагментов и документов в скоупе, а не по оценке.

- R0 САМОПРИМЕНЕНИЕ: ни один документ не коммитится при противоречии корпусу. Каждое положение проверяется на конфликт с ADR-L0-000001…ADR-L0-000013; конфликт устраняется правкой либо регистрируется в разделе «Сознательные отклонения» по чартеру §7. Решение об устранении правкой либо о регистрации отклонения принимает Оператор. Метафоры заменяются терминами глоссария до коммита.
- R1 ЕДИНСТВЕННАЯ ТОЧКА: все идеи и решения Оператора фиксируются только здесь. Других мест накопления нет.
- R2 ЯЗЫК И РЕГИСТР: русский; технический регистр; термины только из глоссария; метафоры запрещены.
- R3 APPEND-ONLY: записи дополняются. Удаление записи выполняется в двух случаях: (а) при наличии четырёх флагов и совместном решении Оператор+LLM; (б) при диспозиции СИНТЕЗ или ЗАМЕЩЕНИЕ — по совместному решению Оператор+LLM на этапе регистрации. Других оснований для удаления записи нет.
- R4 СЕРИЙНОСТЬ: в работе находится строго одна идея. Активная запись (дефиниция в разделе 2) — единственная. Фиксация (Ф1) выполняется параллельно и не ограничена: наличие Ф1 не блокирует другие записи. Работа над записью начинается с установки Ф2.
- R5 ВНЕДРЕНИЕ НА ВЕСЬ КОРПУС: одобренная идея изменяет все документы корпуса, которые затрагивает, в одном исполнении. Частичное внедрение запрещено. Операциональное определение: «весь корпус, который затрагивает идея» = скоуп записи.
- R6 ДИНАМИЧЕСКАЯ ОЧЕРЕДЬ: записи класса МЕЛКАЯ ПРАВКА размещаются в начале очереди; записи класса КРУПНАЯ ДОРАБОТКА — в конец. Мелкие правки закрываются первыми; объём крупных доработок уменьшается по мере закрытия мелких правок. Порядок очереди вычисляется по настоящему правилу и не хранится в файле. Хранение порядка запрещено.
- R7 ZERO-ШАБЛОН: корпус — нулевой шаблон. Эратумы, новые ADR и чейнджлоги не создаются. Все версии документов — 1.0.0. Внедрение идеи = прямая правка текста корпуса.
- R8 ПЕРЕГРУЗ СЕССИИ: если внедрение не укладывается в одну сессию или один scope-lock T1 — работа останавливается. Идея фиксируется в файле DEBT (./aedis/governance/specs/debt/) с последовательностью документов (зависимости первыми). Молчаливое дробление запрещено (чартер §6).
- R9 ПАМЯТЬ КОНТУРА: промежуточное состояние и полное описание текущей задачи фиксируются в памяти контура (state-файл) для продолжения в чистой сессии.
- R10 АНТИДУБЛЬ: при регистрации новой идеи контур LLM выполняет поиск похожей невнедрённой записи. Критерий похожести до появления линтера определяется полным обсуждением Оператор+LLM: контур LLM выполняет поиск, Оператор направляет поиск. При совпадении диспозиция определяется до регистрации: СИНТЕЗ (обе идеи объединяются в одну запись, прежние записи удаляются) или ЗАМЕЩЕНИЕ (старая запись удаляется с фиксацией причины, регистрируется новая). Идея без определённой диспозиции не регистрируется. Параллельное существование двух близких идей запрещено.
- R11 ПОЛНАЯ СВЕРКА ПРИ АВТОРИНГЕ: перед ратификацией текста контур LLM выполняет сверку по полному списку запрещённых конструкций Strict AEDIS CommonMark Profile (раздел Forbidden AST профиля 1.5), а не по выборочным пунктам. Самопроверка исполнителя не является достаточной верификацией; финальная сверка выполняется по чек-листу Forbidden AST целиком, включая текстовые блоки и плейсхолдеры шаблонов.
- R12 СКОУП ОБЯЗАТЕЛЕН: скоуп каждой идеи определяется при регистрации — до анализа решения и до внедрения. Флаг 3 не выдаётся без зафиксированного скоупа. Флаг 4 сверяет фактический diff по commit SHA исключительно со скоупом: любое расхождение diff со скоупом = провал верификации, эскалация Оператору по §P6. Скоуп полный независимо от класса записи: перечисляются все затрагиваемые документы и фрагменты.
- R13 БЛОКИРОВКА: если закрытие активной записи невозможно без выполнения другой записи, работа над активной записью останавливается. В активную запись вносится поле ОЖИДАЕТ: [IDEA-YYYY-NNN] — ссылка на блокирующую запись. Блокирующая запись регистрируется (Ф1) и получает Ф2; после её закрытия ожидающая запись активируется. Цепочка блокировок глубиной более 3 — эскалация Оператору: решение о расширении скоупа или об остановке (связка с R8). Граф ОЖИДАЕТ-ссылок обязан быть ацикличным; циклическая ссылка запрещена.

## 3. ЖИЗНЕННЫЙ ЦИКЛ: ЧЕТЫРЕ ФЛАГА

Идея считается выполненной только при наличии всех четырёх флагов рядом с записью.

- Ф1 ВЫСКАЗАНО ОПЕРАТОРОМ: verbatim-текст. Ставится немедленно при регистрации (операционализация чартера §5: немедленная регистрация, а не немедленная ратификация). Фиксация параллельна и не ограничена. При регистрации декларируется скоуп (R12); диспозиция при совпадении определяется до регистрации (R10).
- Ф2 ПОНЯТО LLM: контур LLM формулирует переформулировку на техническом языке. Ф2 устанавливается только на активную запись. Если однозначная переформулировка невозможна — флаг не ставится, идея возвращается Оператору.
- Ф1+Ф2 ОДОБРЕНЫ СОВМЕСТНО: ЖЕЛАТЕЛЬНО совместное обсуждение Оператор+LLM с ожиданием позиции LLM. Данный шаг не является блокирующим условием перехода.
- Ф3 РЕЗОЛЮЦИЯ: ОДОБРЕНО ВНЕДРЕНИЕ. Вердикт Оператора в интерактивной сессии (Verification Seal, §P6). Вердикт не выдаётся без зафиксированного скоупа. Исходы: ОДОБРЕНО, ОТКЛОНЕНО (с причиной), ДУБЛЬ (со ссылкой). Диспозиция отклонённых и дублирующих записей определяется при внесении (R10); нерешённая запись не вносится. При одобрении параллельно регистрируется запись DEBT в ./aedis/governance/specs/debt/ по чартеру §6.
- Ф4 ВНЕДРЕНО: Gemini исполнил задачу T1; Kimi верифицировала diff по commit SHA со скоупом записи; Оператор и LLM совместно принимают решение «в архив» — и только после этого запись удаляется.

Обработка записей DEBT на стадии разработки не выполняется: все записи DEBT будут удалены к релизу шаблона, формальная обработка по DEBT-FSM (ADR-L0-000001/R2.3) отложена. См. раздел «Сознательные отклонения».

## 5. ПОРЯДОК РАБОТЫ

1. РЕГИСТРАЦИЯ: идея озвучена → контур LLM выполняет проверку R10, Оператор направляет поиск → при совпадении: диспозиция СИНТЕЗ или ЗАМЕЩЕНИЕ до регистрации → скоуп формулирует контур LLM под направлением Оператора, утверждает Оператор (R12) → запись с флагом 1.
2. ПОНИМАНИЕ: переформулировка контуром LLM (флаг 2) → ЖЕЛАТЕЛЬНО совместная сверка с Оператором. Ф2 устанавливается только на активную запись.
3. БЛОКИРОВКА (условный шаг): при невозможности закрыть активную запись без другой записи — R13: поле ОЖИДАЕТ, блокирующая запись регистрируется и получает Ф2.
4. РЕЗОЛЮЦИЯ: вердикт Оператора (флаг 3) при зафиксированном скоупе.
5. ИСПОЛНЕНИЕ: Kimi авторит задачу T1 (scope-lock на все затрагиваемые документы; scope-lock T1 идентичен скоупу записи) → Gemini исполняет без интерпретации → синхронизация с GitHub.
6. ВЕРИФИКАЦИЯ: Kimi проверяет diff по commit SHA против T1 и сверяет diff со скоупом записи. Расхождение diff со скоупом или провал против T1 — стоп по §P6, эскалация Оператору.
7. АРХИВАЦИЯ: совместное решение Оператор+LLM (флаг 4) → запись удаляется из файла → ожидающая запись, ссылавшаяся на неё полем ОЖИДАЕТ, активируется.

## 6. ОЧЕРЕДЬ

Очередь динамическая. Порядок очереди вычисляется по правилам R6 и R13 и не хранится в файле. Приоритет: (1) блокирующая запись — цель поля ОЖИДАЕТ активной записи; (2) записи класса МЕЛКАЯ ПРАВКА по дате регистрации; (3) записи класса КРУПНАЯ ДОРАБОТКА. Класс определяется формальным критерием скоупа (раздел 2). Смена класса записи является совместным решением Оператор+LLM.

## 7. ЗАДАЧИ НА ПРОРАБОТКУ

Задачи, порождённые работой с этим файлом. Закрываются до релиза шаблона.

- TASK-001: Новая папочная система: структура каталогов бандла по ADR-L0-000001/R8; отклонения от скелета регистрируются как instantiation gap.
- TASK-002: Реестр FSM-токенов жизненного цикла идеи по ADR-L0-000005. Формат: STATE_ + SCREAMING_SNAKE_CASE. Токены: STATE_IDEA_DECLARED, STATE_IDEA_UNDERSTOOD, STATE_IDEA_APPROVED, STATE_IDEA_IMPLEMENTED. Поле статуса шаблона записи переводится на реестр токенов. Линтер-проверки реестра: не более одной активной записи; ацикличность графа ОЖИДАЕТ; отсутствие висячих ОЖИДАЕТ-ссылок.
- TASK-003: Заголовки FILE_MUTATION и SPDX-лицензии на все файлы репозитория.
- TASK-004: Регистрация терминов в глоссарии: idea/идея, flag/флаг, drift/дрейф, resolution/резолюция, queue/очередь, rework/доработка, scope/скоуп.
- TASK-005: Перевод правил R0–R13 в EARS-формат: детерминированные REQ-ID документно-локального формата по ADR-L0-000004, трейлеры "| Verification: test_target_name()" на каждое требование. Идентификаторы R&lt;NN&gt; являются машиночитаемыми документно-локальными токенами (дефиниция в разделе 2); линтер сверяет диапазон с фактическим максимальным R-ID. До закрытия TASK-005 правила данного файла не имеют нормативной силы; файл сохраняет статус ненормативной поверхности.
- TASK-006: Валидация данного файла Strict AEDIS CommonMark Profile (ADR профиля 1.5): ручная сверка до появления машинного линтера; профиль применён к тексту на стадии авторинга, машинная проверка отложена.
